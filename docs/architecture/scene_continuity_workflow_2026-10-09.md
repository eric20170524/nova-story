# 单场分镜连续性与分轮制作实施方案

单场生成读取按故事时间维护的状态，单镜出图读取对应动作时刻的状态。先建立可回放的连续性记录，再分轮补充衣着、道具、背景与画面检查。每批独立验收，保留已确认的事实和已有制作成果。

任务勾选状态只在 [0_TASKLIST.md 的 Track 5 S5](../0_TASKLIST.md#track5-s5-continuity) 维护，编号 CT00 至 CT22。本文规定设计、依赖和验收，不把任务列入计划等同于功能已实现。

**当前范围**：2026-10-09 根据第三方静态评审修订方案与任务清单，业务实现未随文档更新。后续从 CT01 记录基线开始；本次不触发正式章节生成、时间线替换或批量出图。

## 评审采纳与判断边界

采纳八项落地决定：分清九机位与整章采纳接口；第一批实现保留旧图的失效标记；单独保存动作进行时状态；分离引文与规范值并关闭未经确认的入账路径；实物身份独立于素材库；限定单场写入范围；冻结模型评估类别与口径；逐调用点管理预算和重试。同步补充夹具、哈希、旧项目操作、页面验收及批次依赖。

## 制片实践与产品原则

实拍经常不按故事顺序进行，场记会按场次和故事日拆解人物、动作、服装及道具，并用文字和照片记录连续性。对应到本项目，应让故事时间决定状态、制作顺序决定排队，避免先生成的图片影响尚未确认的剧情事实。[ScreenSkills 场记职责](https://www.screenskills.com/job-profiles/browse/film-and-tv-drama/technical/script-supervisor-film-and-tv-drama/)

服装部门会预先识别剧情中的服装变化，并维护准确的连续性记录。项目中的一件外套可以有干燥、湿透、破损等参考版本；这些版本对应同一件物品，不能因换图而变成另一件衣物。[ScreenSkills 服装连续性职责](https://www.screenskills.com/skills-checklists/scripted-film-and-tv/costume-department/standby-costume-assistant-skills/)

具体软件契约及批次安排是基于上述实践提出的项目设计，不是行业规范原文。

必须保持的原则：

- 来源事实、已确认改编、视觉设计选择分别记录。模型建议不能自行成为已确认事实。
- 每场保存入场状态、本场变化、出场状态；每个动作变化有明确发生位置。
- 衣物与物体按实物身份追踪。湿度、破损、颜色和持有者分开，不用一段描述互相覆盖。
- 未拍到不等于消失，未说明不等于不存在；没有依据不能清空或恢复状态。
- 同一时刻的机位候选共享状态；动作前后镜头使用不同状态。
- 无依据的修复、清洗、补充、换装或物件替换不得自动发生。
- 图片与事实不符时修图片；只有明确修改剧情或设计，才产生新的事实或设计版本。
- 制作分轮可以暂缓次要视觉细节，不能把人物、关键道具和关键变化的冲突标成完成。

## 第一批冻结的数据契约

第一批只支持时间关系已确认的线性故事段。共同持有、无法判断的跳时等保留证据并进入 `pending_review`，不丢掉其中一个人物，不擅自沿用或重置状态；扩展分别归 CT20/CT21。

### 实物身份、属性与证据

| 对象 | 最小字段及职责 |
| --- | --- |
| 实体 | 独立 `continuity_entity` 身份：entity_id、project_id、kind、display_name、aliases、可选 parent_entity_id/character_id；可选绑定资产 ID 和参考版本 |
| 故事位置 | story_segment_id、script_scene_id、screenplay_order_revision、场次在剧本中的顺序、beat_id、节拍内变化序号、moment_id/phase |
| 状态格 | entity_id、attribute_id、typed value、knowledge_status、有效范围、确认来源及证据引用；关系值只能引用实体 ID |
| 变化 | change_id、源文/绑定版本、故事位置、目标实体、操作、读前置条件、写结果、确认来源、修订号 |
| 场次快照 | entry_state、confirmed changes、exit_state、对应版本、state_hash、source_hash、依赖；另存各 moment 的状态引用 |
| 镜头引用 | script_scene_id、beat_id、moment_id/phase、snapshot ID/修订、选中实体及属性、设计版本、素材参考版本 |
| 制作状态 | continuity_status 与制作轮次、图片生成状态分别保存；pending_review、conflict、stale 不等于缺图 |

实物表不采用素材库的名称唯一约束。两把都叫“黑伞”的实物有两个 ID，可以共享同一款设计资产；资产改名或换图不改变实物身份。人物实体关联现有角色 ID，无资产的衣物/物件也可先登记。导入和复制须重映射实物、组件、关系与证据引用，禁止跨项目引用。

采用**封闭、带版本的属性注册表**，定义类型、适用实体、允许值、持久范围和操作。第一批支持人工/规则确认的 color、wetness、integrity、wearer、holder、owner、location、presence、open_state、lock_function、power_state；模型能否提取是另一项资格。CT10–CT12 完善提取和编译，不重复把基础注册当作模型能力。未知属性保留原建议，不能写入已确认快照；新增属性或改变语义须提升 schema/状态策略版本。

每件衣物自己的 wearer、color、wetness、integrity 分格存放；一个人物可持多件物品。门板与门锁登记为不同组件实体，分别使用 integrity 与 lock_function，不能从门板完整推断锁可用。第一批 holder 只支持单一实体或已确认无人持有；共同持有进入待核对。

`evidence_quote`、`source_document_id`、`source_revision`、`source_text_hash`、`start/end` 与规范 value 分开。偏移按该版本文本的 UTF-16 code unit、左闭右开计算；quote 必须等于该范围原文。文本或绑定改版须重新验证，小说和改编句子的偏移不能互用。`wetness=wet` 不要求英文 wet 是中文原文子串；引文“外套湿透了”与值映射由具名规则或人工确认。视觉设计依据使用独立 design ID/修订，不伪造原文引文。

操作先实现 assign、clear、completed transfer。clear 写“已确认无此关系”，不删除记录或变成 unknown；缺字段、unknown、confirmed null 三者不同。transfer 检查同一物件的旧 holder 前置条件，再原子更新关系；递出、意图、否定不能当作已完成转移。数量运算留到 CT21。

新快照只接纳白名单确定性规则或人工确认的变化；规则有 ID/版本、适用条件、正反例。模型、自审及旧 `evidencedContinuityStates` 过滤后的 `fact.states` 均只能作为建议，不能借旧写入路径升级确认。旧字段可读用于迁移，但不得作为新快照可信状态回退。初始资产外观只有在明确确认成设计依据后才能入账，不能覆盖剧情变化。

### before、during、after 与故事顺序

before 是该事件提交前的持久状态；after 是其已确认变化提交后的持久状态。during 必须另外保存 `during_overlay`：moment_id、所属事件、已完成子事件位置、可见属性值、证据/设计版本和确认来源。它叠加到该时刻之前已提交的持久状态上，不写回 exit，也不能从 after 倒推。第一批 moment 可见位置只支持 held/airborne/on_surface 及可选锚点实体 ID，作为版本化的瞬时字段；不得把 in_air 当作 location 的实体 ID，复杂空间关系留到 CT21。

例如原文明确“杯子从手中滑落，仍完整地悬在半空，随后落地碎裂”：before 为完整/在手中；during 用已确认的 airborne 和 holder=null overlay，完整度来自未碎裂的前态；after 为破碎/地面、无人持有。原文只有“杯子掉落摔碎”时，若选中间关键帧，悬空位置和取帧时刻须经明确的镜头设计确认；无法确定时待核对，不自动用碎杯代替。多个中间时刻各建 moment，不能用一个 during 枚举涵盖不同物理时刻。

故事次序只来自稳定剧本场次、节拍和变化顺序及其版本。`scene.index` 是制作时间线显示顺序；coverage promote 的插镜、排序和同刻替换不得修改故事顺序版本或重放事件。

### 哈希与依赖

CT04 固定两种规范化预像，以规范 JSON 的 UTF-8 字节计算 SHA-256：

- `state_hash`：schema/状态策略版本、故事位置、已确认实体与类型化状态格、明确的 unknown/null 标记及 during overlay。对象键固定序列化；无序实体按 entity_id，状态格按 entity_id/attribute_id，集合关系按完整目标 ID 排序。旧 wardrobe 结构须先分配 item entity_id，不能只按 entity:attribute 排序。
- `source_hash`：剧本及原文精确内容哈希、事实/绑定版本、故事顺序版本、实体映射版本、确认/设计版本、按故事顺序排列的变化和证据范围、输入 state_hash。新连续性依赖纳入现有候选来源哈希及采纳校验；旧策略候选不得自动通过。

ID、修订和语义相同的无序输入排列应有相同哈希；事件顺序属于语义，不能为了排序稳定而重排。时间戳、请求 ID、耗时、模型输出顺序等运行元数据不入预像。原始文本哈希不折叠空白或换行，不破坏证据偏移。证据改版即使值相同，也改变 source_hash；state_hash 可保持相同。

镜头另存实际读取的实体/属性、事实/绑定、时刻、设计及参考版本依赖。全局修订用于重新验证，不等于所有图片都要重做：镜头实际输入和证据依赖未变时，可记录重新验证后复用。

## 状态回放、接口与写入范围

流程为：定位故事位置 → 读取适用的已确认前态 → 提取并核对本场变化 → 程序回放 → 保存入场/出场快照 → 规划镜头 → 按镜头时刻装配事实与状态 → 翻译编译 → 校验 → 出图核对。

关键行为：

1. 单场请求显式带 `target_scene_id`，只读已确认的前序变化/快照或指定入口。缺必需前态时待核对，不恢复为资产默认。只允许写目标场次的建议、候选、进度和快照；不为其他场次调用提取/规划/翻译，不写其建议、候选、镜头或时间线。确认修订后的下游重新验证是独立操作，不能隐藏在预览中；CT06 须收窄当前整章循环。
2. 程序按故事顺序回放，与调用、重试、渲染或完成顺序无关。相同已确认输入得到相同输出哈希。
3. 场内变化逐项应用，镜头读取 before/during/after 对应 moment；进行中按独立已确认 overlay 装配，场末状态不能覆盖全场镜头。
4. 场次快照保留相关实体及持续变化；镜头仅选择需要展示的实体和属性。裁切、离画或角色暂时缺席不删除状态。
5. 新场地取消不适用的站位，不取消角色随身衣物与道具；留在原场地的门锁、碎片等在回到该地时仍可恢复查询。
6. 候选变化、已确认连续性及已采纳时间线使用独立修订。生成候选本身不得改已确认账本或已采纳镜头；人工确认是独立操作，可修订账本并标记依赖镜头过期，但不自动采纳。已确认计划与成图偏差分开记录。
7. 保留原始来源及绑定。只把本场需要的状态交给模型，完整状态由程序保存，禁止为了输入预算截掉关键证据。

## 改动、失效与旧项目

第一版确认修订后，从最早受影响故事位置重放同一已知线性段所有可能受影响的后续已确认变化，逐场比较状态与证据依赖。**不在下一条 assign 处提前停止**；转移依赖旧 holder，同件衣物其他属性也独立延续。将来只有证明属性读写依赖和关系闭包完整，才可另行优化截止算法，并增加反例验收。

CT05 实现事务内按镜头 `markContinuityStale` 服务操作：保存过期原因、旧/新依赖版本和受影响属性；保留 scene 原行、scene_version、coverage、参考快照及旧 asset_url。生成状态与 continuity_status 分开，旧图仍可打开对照；无关镜头 asset_url 和版本不变。禁止以整章替换、删除引用或清空图片地址实现失效。只存 `script_change.result_json` 不满足可见旧图要求。

## 分轮制作与局部采纳

| 制作轮次 | 交付 | 继续制作的条件 |
| --- | --- | --- |

草稿可以逐轮增加，但“完成”仍需覆盖必要动作及声音来源。视觉覆盖程度和事实一致性是两套检查，不能为了草稿放行而关掉后一套。

九机位扩展只改变构图、角度和合理的可见范围，保持同一故事时刻。生成、应用、加入时间线三个动作都校验来源状态；加入后不能重复推进持有转移或破损事件。动作推进使用另一镜头/节拍。

“一键生成”按当前版本选取可出图且缺图的镜头。单独列出待核对、冲突、过期及已完成数量；不静默跳过后宣称全部完成。重复点击幂等；重做已有图作为显式动作，保留旧版本。

## 本地 9B 的工作范围

每次只处理一段完整动作或一个小节拍，以及相关实体、已确认入场状态和必要前文。先提人物和实物，再提变化，再核对冲突；只有复杂项才拆成更多调用。程序负责 ID、状态合并、数值、版本、数量及依赖检查。

首轮沿用单推理槽、低温、小结构输出作为校准起点。以下是本次静态基线的**不同调用点**，均需 CT09 独立记录和调整；字符不是 token，2200 不是全流程统一预算。

| 调用点 | 当前边界/行为 | CT09 要求 |
| --- | --- | --- |
| 人物绑定 `proposeBinding` | 正文与上下文合计 2200 字符；temperature 0.1、maxTokens 256 | 保留出入场等必要前文；超限按语义拆分或待核对 |

- **自动接受资格（默认关闭）**：按属性另设独立确认策略、预先冻结的资格样本和非零明确自动完成目标，再做独立评估；不能因 CT14 建议可用而开放。报告已接受总数、接受错误数、明确案例自动完成率、歧义强解率和误拦截。接受数为零时错误接受率=N/A；该组有明确错误自动接受即不具资格，小样本不证明所有属性可靠。
